# Learning guide: Java, Spring Boot and SQL

This guide is a map through the project. Work through the requests yourself rather than only reading the source.

## 1. Follow one request through the application

For a new router, a client sends `POST /api/v1/devices` with JSON. The path through the code is:

1. `NetworkDeviceController.create()` receives the HTTP request. `@Valid` asks Bean Validation to check the request record.
2. `CreateDeviceRequest` defines which fields are allowed and their constraints. `@NotBlank`, `@NotNull` and `@Size` check values; `@IpAddress` invokes the custom IPv4/IPv6 validator.
3. `NetworkDeviceService.create()` applies the business rule that one IP address can be assigned to only one device. It normalises the address and creates the entity.
4. `NetworkDeviceRepository` extends `JpaRepository`. Calling `save()` asks Spring Data JPA/Hibernate to persist the entity.
5. Hibernate converts the Java object into SQL and sends it to the relational database.
6. `DeviceResponse.from()` maps the saved entity to a response DTO. The controller returns HTTP 201 Created.

**Why separate the layers?** The controller deals with HTTP. The service owns business rules. The repository handles persistence. Keeping those responsibilities separate makes the system easier to test and maintain.

## 2. Understand the database structure

The migration `src/main/resources/db/migration/V1__create_network_devices.sql` creates one table named `network_devices`.

- A **table** is a structured collection of records.
- A **row** represents one device.
- A **column** is one attribute, such as `name`, `device_type` or `ip_address`.
- The **primary key** (`id`) uniquely identifies each row. It is generated by the database.
- The **unique constraint** on `ip_address` stops two rows from storing the same address.
- An **index** helps the database find matching rows more efficiently. Indexes improve lookups but take extra space and make writes a little more expensive.
- `VARCHAR(120)` stores text with a maximum length. `TIMESTAMP WITH TIME ZONE` stores a date/time with time-zone information.

The Java `NetworkDevice` class is a JPA entity mapped to that table. `@Column` connects a Java field to a database column; `@Enumerated(EnumType.STRING)` stores enum names such as `ROUTER` and `ACTIVE` as text, not as fragile ordinal numbers.

## 3. Practise SQL

Open `docs/sql-practice.sql` in your SQL client. Run each query separately and inspect the result.

- `SELECT` reads data.
- `WHERE` filters rows.
- `LIKE` supports partial text matching.
- `COUNT` returns a count.
- `GROUP BY` groups rows so aggregate functions can calculate totals per category.
- `UPDATE` changes existing rows. Always add a `WHERE` clause unless you intentionally mean to update every row.
- `DELETE` removes rows. Check the ID first and use a transaction when practising on important data.

Useful additional PostgreSQL commands in `psql`:

```sql
\dt                         -- list tables
\d network_devices          -- inspect one table
SELECT current_database();   -- see the active database
SELECT version();            -- see the PostgreSQL version
```

## 4. Try the API

Start the app locally, open Swagger UI, and create two different devices. Then try each operation:

1. Create a router and note the returned `id`.
2. List all devices.
3. Filter with `?type=ROUTER&status=ACTIVE`.
4. Search with `?q=router`.
5. Retrieve the record by ID.
6. Change its location and status using PUT.
7. Try to create another device with the same IP; expect HTTP 409 Conflict.
8. Try an invalid address such as `999.999.1.1`; expect HTTP 400 Bad Request.
9. Delete the test device; expect HTTP 204 No Content.

The HTTP status is part of the API contract: 201 means created, 200 means successful read/update, 204 means deleted, 400 means invalid input, 404 means missing record, and 409 means a conflict.

## 5. Run the automated tests

```powershell
mvn test
```

The integration tests start the application with an isolated H2 test database and exercise the API over MockMvc. They are designed to cover CRUD operations, filters, duplicate IP protection, IPv4 validation, IPv6 normalisation and not-found handling.

## 6. Local database versus hosted database

By default, `application.properties` uses an H2 in-memory database. It starts automatically and needs no credentials, but its data disappears when the process stops.

For a persistent hosted demo, set the PostgreSQL connection details as environment variables. Flyway applies the versioned SQL migration at application startup; Hibernate uses `ddl-auto=validate` to check that the entity mapping matches the database schema. The database password should be stored in the Render dashboard, never in Git.

## 7. Security boundary

This is intentionally a learning/demo API without authentication or authorisation. Do not put real customer data into it. Before production use, add identity and access control, rate limiting, structured and privacy-safe logging, backups, monitoring, secret rotation and a deployment process that protects database migrations.
